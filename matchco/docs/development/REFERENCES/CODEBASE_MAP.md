## System Overview

MatchCo is a multi-tenant SaaS platform built on **Django** + **PostgreSQL schemas** (via `django-tenants`) for tenant isolation. The platform combines:

- **LMS** — courses, modules, quizzes, learning trails, gamification, certificates
- **Recruitment engine** — bilateral job matching (Porta Match), structured job postings (Porta Vaga), QR-driven signup, LGPD-compliant candidate data
- **Content management** — wiki, feed (announcements), documents with versioning and approval workflows
- **Real-time features** — WebSocket-based course chat, notifications (email, push, SMS, webhook)
- **Admin console** — operator back-office for content, users, integrations, and analytics
- **Partner/mobile APIs** — REST endpoints for external integrations and mobile apps

**Current version:** `v2.0.0-alpha.2` (SemVer with git tags, gh releases, conventional commits)

## Core Architectural Patterns

### 1. Multi-Tenant Isolation (django-tenants)

**Tenant Detection:**
- `TenantMainMiddleware` reads the HTTP `Host` header, matches it against `configuration.Domain.domain`, and switches the PostgreSQL schema for that request
- `OrganizationContextMiddleware` allows users to override their active tenant by reading `session['selected_organization_id']` and calling `connection.set_tenant()` (Slack-style workspace switcher)

**Schema Layout:**
- **Public schema:** Organizations, Memberships, Users, Accounts, Recruitment, Console, Chat, Search
- **Per-tenant schemas:** Courses, Students, Publishing, Documents, Audience, Library, Gamification, Learning

**Mirror Models (`tenants_core`):**
- Signal-driven: `User`, `Organization`, `Company` changes fan out to all tenant schemas as `TenantUser`, `TenantOrganization`, `TenantCompany` to allow FK references without cross-schema joins

### 2. Authentication & Authorization

**User Model:** `user_management.User` (custom, extends `AbstractUser`)
- Case-insensitive unique email
- Custom backend: `accounts.backends.EmailOrUsernameBackend` (login with email OR username)
- Activation: email confirmation → `PublicConfirmEmailView` activates both user and Membership
- Rate limiting: 10/h on login, 5/h on public signup (via `django-ratelimit`)

**Organization Access:** `configuration.Membership`
- Scopes user to a specific `Organization`, `Company`, `BusinessUnit`, `OperationalUnit`
- Roles: `owner`, `admin`, `member`, `guest`, `viewer`
- `ActiveOrganizationMiddleware` validates membership on every request, auto-selects primary, redirects to `no-access` if revoked

**Superadmin Mode:**
- `session['selected_organization_id'] = '__all__'` disables tenant filtering
- Both middleware skip tenant validation; `request.active_organization_id = None`

### 3. Content Eligibility (audience)

`AudiencePolicy` + `AudienceRule` define **who can see content**:
- Scoped by organization, company, business unit, function, channel, role, person type, program membership
- Match mode: ALL rules must pass, or ANY
- Service entry point: `EligibilityService.can_view(user, content)` → boolean
- Used by console, publishing, courses, documents, learning to filter visibility

### 4. Event-Driven Gamification & Notifications

Central dispatcher: `learning.services.track_event(user, event_type, object, ...)`
- Records `ContentEvent` to the event stream
- Immediately awards points (via `learning.PointLedger`)
- Enqueues webhook deliveries
- Triggers badge/challenge progression

Called from:
- Course enrollment/completion (courses app)
- Quiz attempts (students app)
- Publication views (publishing app)
- Login (accounts app)
- Application status changes (recruitment app)

### 5. Recruitment as a Ports & Adapters Pattern

The recruitment app uses hexagonal architecture:
- **Ports** (`integrations/ports.py`): `IdentityPort`, `AssessmentPort`, `NotificationPort`, `FilePort` — abstract interfaces
- **Contracts** (`integrations/contracts.py`): frozen dataclasses (`PersonRef`, `AssessmentRequest`, `NotificationRequest`, `FileRef`)
- **Registry** (`integrations/registry.py`): resolve adapters by port and provider name
- **Defaults** (`integrations/defaults.py`): no-op fallback implementations (QR signup never breaks on integration failure)
- **Providers** (`integrations/providers/`): concrete implementations (HRIS, assessment, notification, file storage)

### 6. LGPD Compliance (Brazilian Data Privacy)

Baked into the recruitment data model:
- **`CandidateIdentity`**: Global person record (UUID primary key, email-based dedup, hashed CPF)
- **`CandidateConsent`**: Granular LGPD consent per `(identity, organization, purpose)` with legal basis enum and `revoked_at` timestamps
- **`RecruitmentAuditEvent`**: Append-only audit log of data access and sensitive actions
- **`Ledger`**: Canonical immutable ledger — `.update()` and `.delete()` raise `LedgerAppendOnlyError`
- **Public LGPD routes** (`/candidato/dados/*`): data export, correction, anonymization (LGPD articles 18–19)

### recruitment — Matching Engine & Candidate Management

**Exports:**

**Key files:**
| File | Tokens | Purpose |
|---|---|---|
| `models.py` | ~120k | 60+ models (identity, position, matching, scoring, audit, ledger) |
| `services.py` | ~35k | Business logic (registration, matching, application SLA, LGPD) |
| `matching.py` | ~4k | rank_candidates(), calculate_match() |
| `scoring.py` | ~8k | ScoringEngine, ScoringRuleManager |

| `feed.py` | ~5k | Territorial opportunity feed builder |
| `tasks.py` | ~8k | Celery tasks (SLA, retention, notifications) |

**Core Workflows:**
1. **QR Signup** → `EntryPointResolveView` → optional PIAG validation → candidate portal signup → `register_candidate()` → consent records
2. **Position matching** → `rank_candidates()` → evaluates all candidates → `CandidatePosition.calculate_match()` (skills 35%, location 35%, salary 20%, exp 10%)
3. **Relation state machine** → notice_delivered → person_interested → employer_interest_view → employer_interested → matched → contact_enabled → response_created → closed (strict forward-only transitions)
4. **SLA escalation** (Porta Vaga) → application created → escapes to store → shopping pool → external pool at configured windows

**Gotchas:**
- Matching algorithm deterministic but can be expensive; caches results in `CandidatePosition`
- Relation state machine is **strict**: invalid transitions raise `RelationStateError`
- LGPD consent model is immutable; revocation never deletes, only sets flag
- Ledger is append-only; `.update()` and `.delete()` are prohibited
- EntryPoint PIAG validation checks `tamper_evidence_hash` and `activation_tested_at`

### learning — Events, Gamification, Trails, Notifications, APIs

**Exports:**

- `BadgeDefinition`, `UserBadge`, `LearningChallenge` — gamification

**Key service:**
- `track_event(user, event_type, object, ...)` — called from every other app on content interactions; records event, awards points, enqueues notifications, advances trails

**Role in platform:**
- The reactive/analytics engine — everything feeds into `ContentEvent` stream
- Console reads `ContentEvent` and `PointLedger` for metrics dashboards
- Closes the loop: content consumption → points → badges → notifications → trail completion → certificates

**Gotchas:**
- `track_event()` is synchronous for point awarding but enqueues async for webhooks
- Certificate issuance is reactive — triggered on `COURSE_COMPLETED` event
- Trail progress is not automatically advanced; requires explicit `mark_trail_step_done()` calls

## Data Flow

### Request Flow: Authenticated User Accessing `/app/`

```
User visits https://acme.matchco.com/app/courses/

1. TenantMainMiddleware:
   - Reads Host: acme.matchco.com
   - Queries Domain.domain = 'acme.matchco.com' → Organization.schema_name = 'acme_tenant'
   - Switches schema_name on database connection

2. OrganizationContextMiddleware:
   - Reads session['selected_organization_id'] (null for most users)
   - For users with workspace selection, calls connection.set_tenant() to override

3. AuthenticationMiddleware:
   - Loads user from session

4. ActiveOrganizationMiddleware:
   - Validates user.Membership for selected org
   - Checks if Membership is active
   - Sets request.active_organization_id, request.active_membership, request.active_role

5. URLRouter:
   - Matches /app/courses/ → StudentCourseListView

6. StudentCourseListView:
   - Queries CourseEnroll for request.user
   - Filters by audience_policy eligibility via EligibilityService.can_view()
   - Returns course list

7. Template rendering:
   - Calls context_processors.navigation()
   - Injects navigation_items, organization_terminology, MATCHCO_VAPID_PUBLIC_KEY
```

### Event Flow: User Completes a Quiz

```
User submits quiz on /course/123/play/

1. save_quiz_view (AJAX endpoint):
   - Validates CourseEnroll for request.user
   - Scores quiz (UserQuizAttempt, UserAnswer)
   - Checks if passing

2. Gamification hook:
   - If passing and first attempt, calls learning.services.track_event(user, 'QUIZ_COMPLETED', quiz, ...)

3. track_event() in learning.services:
   - Records ContentEvent to event stream
   - Awards points: PointLedger.create(points=<calculated>)
   - Checks for badge thresholds → UserBadge creation
   - Enqueues NotificationDelivery tasks (email, push, SMS, webhook)
   - Checks trail progress → advances if quiz is a trail step

4. Trail advancement:
   - If quiz completes a TrailStep, marks TrailProgress.done = True
   - Checks if all steps in TrailAssignment are done → CourseCertificate issuance
   - Enqueues CERTIFICATE_ISSUED notification

5. Celery worker (async):
   - Picks up NotificationDelivery tasks
   - Sends email, push, SMS, webhooks to external systems
```

### Recruitment Flow: QR Signup → Matching

```
Candidate scans QR code at a store:

1. EntryPointResolveView (/qr/<uuid>/):
   - Validates EntryPoint.state = 'active'
   - Checks PIAG (tamper_evidence_hash, activation_tested_at)
   - Redirects to canonical_destination_url

2. CandidateSignupView (/candidato/vaga/cadastro/):
   - or MatchcoSignupView (/candidato/signup/) depending on mode
   - POST: calls services.register_candidate(email, cpf, job_functions, ...)
   - Creates or retrieves CandidateIdentity (email-normalized dedup)
   - Creates CandidateProfile (org-scoped)
   - Creates CandidateConsent records (visibility_match, circulation)
   - Optional: fires IdentityPort (HRIS integration) — soft-fails

3. Onboarding:
   - CandidateOnboardingJobFunctionsView — select job functions
   - CandidateProfileSurveyView — answer questionnaire
   - CandidateOnboardingCompleteView — mark complete

4. Background: Position Matching:
   - Admin creates Position in Porta Match mode
   - Daily or on-demand: matching.rank_candidates(position)
   - For each org candidate: CandidatePosition.calculate_match()
   - Stores match_score with explanation JSON
   - Delivers Relation records in notice_delivered state

5. Candidate sees opportunity:
   - feed.build_feed() lists Relation records
   - Candidate clicks interest → CandidatoInteresseView → Relation.transition(person_interested)
   - Logs RelationTransitionEvent

6. Employer-side:
   - Recruiter views interest stack (EmployerOpportunityInterestListView)
   - Declares interest (with AA-7 authority) → Relation.transition(employer_interested)
   - On match, enables contact (with AA-8 authority) → Relation.transition(contact_enabled)
   - All transitions logged to Ledger (append-only audit)
```

## Conventions & Patterns

### Naming Conventions

| Category | Convention | Example |
|---|---|---|
| Django app | lowercase | `recruitment`, `user_management` |
| Django model | PascalCase | `CandidateIdentity`, `OpportunityCriterion` |
| Database table (auto-generated) | app_lowercase_modelname | `recruitment_candidateidentity` |
| URL namespace | lowercase (plural common) | `recruitment`, `recruitment_public`, `api` |
| Template path | `app/template_name.html` | `recruitment/candidate_list.html` |
| View class | PascalCase + `View` | `CandidateListView`, `CandidateDetailView` |
| Service function | snake_case | `register_candidate`, `rank_candidates` |
| Signal name | `<app>_<model>_<action>` or Django built-in | `organization_created`, `user_saved` |
| Test file | `test_*.py` or `tests.py` | `test_recruitment_models.py` |

### File Organization

**Models:**
- One `models.py` per app (or `models/` subdirectory for very large apps)
- Public exports at module level (`__all__`)

**Views:**
- `views.py` for class-based views (`CBV` extends `View`, `TemplateView`, `DetailView`, etc.)
- `api_urls.py` for DRF viewsets
- `views.py` calls `services.py` for business logic — never business logic in views

**Services:**
- `services.py` — stateless functions with no DB access across schemas
- Called by views, tasks, signals
- Return simple dataclasses or Django models, not JSON

**Admin:**
- `admin.py` — register models with custom `ModelAdmin` classes
- Inlines for hierarchical editing (e.g., `QuestionnaireQuestionInline`)
- Bulk actions, filters, custom displays

**Signals:**
- `signals.py` — Django signal handlers
- Connected in `apps.py`'s `AppConfig.ready()` method
- Mirror sync (configuration → tenants_core) lives in `configuration/signals.py`

### Permission & Access Control

**Django Permissions (built-in):**
- `add_<model>`, `change_<model>`, `view_<model>`, `delete_<model>`
- Used on `user_management` CRUD views via `@permission_required` or `@any_permission_required`

**Membership-based (custom):**
- `configuration.Membership.role` — (owner, admin, member, guest, viewer)
- `ActiveOrganizationMiddleware` validates on every request
- Used by console to filter organizational data

**Audience policies (content-level):**
- `AudiencePolicy` + `AudienceRule` — who can see what content
- `EligibilityService.can_view()` — entry point

**Authority scopes (recruitment-specific):**
- `AA-1` through `AA-8` — employer-side permissions (declare need, structure, view interest, declare interest, enable contact)
- `EmployerActor.authority_scopes` — list of scopes
- AA-7 and AA-8 require `human_verified_at`

### Async & Celery Tasks

**Synchronous (blocking):**
- All view logic, database queries, `track_event()` points awarding

**Async (Celery):**
- Webhook deliveries (`learning.deliver_webhooks`, `learning.retry_notification_deliveries`)
- Email/push/SMS sending (NotificationDelivery tasks)
- Heavy computation (data exports, report generation)
- Scheduled tasks (SLA escalation, retention enforcement, LGPD)

**Beat schedule** (in `matchco/settings/base.py`):
- `learning.deliver_webhooks` — every 60s
- `recruitment.apply_retention_task` — daily
- `recruitment.send_pending_notifications_task` — every 12h

## Gotchas & Non-Obvious Behaviors

### 1. Tenant Switching Has Two Paths

- **Host-based** (primary): `TenantMainMiddleware` reads Host header
- **Session-based** (workspace switcher): `OrganizationContextMiddleware` overrides via `connection.set_tenant()`

If both disagree, session wins (for users with workspace selection).

### 2. Mirror Sync Is Asynchronous

`configuration/signals.py` fans out `User`, `Organization`, `Company` changes to all tenant schemas via `tenant_context()`. If you create a user and immediately query `tenants_core.TenantUser` in the same request, it may not exist yet.

### 3. Relation State Machine Is Strict

`recruitment.Relation` only allows specific state transitions. Trying to move from `notice_delivered` directly to `matched` will raise `RelationStateError`. The transition graph is encoded in `ALLOWED_TRANSITIONS`.

### 4. Matching Algorithm Is Deterministic but Expensive

`rank_candidates(position)` iterates all org candidates and calls `calculate_match()` for each. Results are cached in `CandidatePosition`, but the first call can be slow for large candidate pools.

### 5. LGPD Consent Is Immutable

`CandidateConsent` records are append-only. Revocation never deletes; it sets `revoked_at` and appends to the audit log. Similarly, `Ledger` records cannot be updated or deleted — `.update()` and `.delete()` raise `LedgerAppendOnlyError`.

### 6. Service Workers Require HTTPS (Except localhost)

The PWA service worker at `/service-worker.js` only works on HTTPS (except for localhost). Local development works, but you can't test PWA features on dev domains without HTTPS.

### 7. reCAPTCHA v3 Is Not User-Facing

reCAPTCHA v3 works silently (no "I'm not a robot" checkbox). Scores are validated server-side with a threshold (default 0.85). Low scores reject the signup; users see no explicit CAPTCHA error.

### 8. Email Confirmation Activates Both User and Membership

`PublicConfirmEmailView` sets both `User.is_active = True` and `Membership.is_active = True`. If Membership already exists, it's activated. If not, one is created.

### 9. Superadmin Mode Is Not a Real Organization

`session['selected_organization_id'] = '__all__'` is a special string, not a real org ID. Both `OrganizationContextMiddleware` and `ActiveOrganizationMiddleware` detect this and skip validation. `request.active_organization_id = None`.

### 10. Content Audience Filtering Is Additive, Not Subtractive

`AudiencePolicy.match_mode = 'ALL'` means all rules must pass; `'ANY'` means any rule passes. There's no "exclude" logic — policies define who CAN see, not who CANNOT.

### 11. Learning Events Are Reactive, Not Proactive

`track_event()` is called by other apps when something happens. There's no background job that generates events. If an app doesn't call `track_event()`, the event never gets recorded.

### 12. Trail Progress Is Not Automatic

Completing the content that is a trail step doesn't automatically mark it done. The step must explicitly call `mark_trail_step_done()`. If it doesn't, the step remains incomplete.

### 13. Notifications Are Per-Channel

A `UserNotification` can have multiple `NotificationDelivery` rows — one per channel (email, push, SMS, webhook). If a user hasn't configured SMS, no SMS delivery is created. The in-app notification still exists.

### 14. Documents Require Explicit Permissions

Unlike publications and courses (which use `AudiencePolicy`), documents require explicit `DocumentPermission` records or `DocumentShareLink` tokens. By default, users see nothing unless granted.

### 15. Media Assets Store Variants (WebP, AVIF)

Images uploaded to the media library are processed into WebP and AVIF variants on save. `MediaAssetServeView` chooses the best format based on `Accept` header.

## Navigation Guide

### To add a new Django app (e.g., `notifications`)

1. `python manage.py startapp notifications`
2. Define models in `notifications/models.py`
3. Register in `matchco/matchco/settings/base.py`: add to `SHARED_APPS` (if cross-tenant) or `TENANT_APPS` (if per-tenant)
4. Add URL include in `matchco/matchco/urls.py` or app namespace
5. Create `notifications/urls.py` with URLconf
6. Create `notifications/views.py` with views
7. Create `notifications/admin.py` and register models
8. Create `notifications/signals.py` if you need to listen to other app events
9. Run migrations: `python manage.py makemigrations notifications && python manage.py migrate`

### To add a new course content type (e.g., `Interactive`)

1. Create a model in `courses/models.py` extending `ItemBase` or as a standalone model
2. Register in `courses/admin.py`
3. Update `ContentCreateUpdateView` in `courses/views.py` to support the new type
4. Create a template `courses/content_<type>.html` for rendering
5. Update `students/views.py` to handle the new type in `StudentContentDetailView`
6. If gamified, call `learning.services.track_event()` for the new action

### To add a new audience filter dimension

1. Add a new enum value to `AudienceRule.dimension` choices
2. Update `EligibilityService.can_view()` to evaluate the new dimension
3. Add a form field in console to allow editing the rule
4. Test with `estimate_policy_reach()` to verify counts

### To add a new recruitment integration (e.g., ATS system)

1. Define the port interface in `recruitment/integrations/ports.py` (e.g., `ATSPort`)
2. Create a frozen dataclass in `recruitment/integrations/contracts.py` for data passing
3. Implement a concrete adapter in `recruitment/integrations/providers/ats_provider.py`
4. Register in `recruitment/integrations/registry.py`
5. Call it from `recruitment/services.py` via `get_adapter('ats', 'provider_name')()`
6. Add a new `IntegrationConnection.integration_type` choice and settings in console

### To add a new Celery task

1. Create `app_name/tasks.py` with `@shared_task` decorated functions
2. Add to `CELERY_BEAT_SCHEDULE` in `matchco/matchco/settings/base.py` if periodic
3. Test locally: `celery -A matchco.celery worker -l info`
4. Dispatch manually: `task_func.delay(args)` or `task_func.apply_async()`

### To add a new notification channel (e.g., Slack)

1. Create a delivery adapter in `learning/integrations/` (or use existing pattern)
2. Update `NotificationDelivery` model to support the new channel
3. Update `UserNotificationPreference` if users can toggle channel preference
4. Call `NotificationDelivery.objects.create(...)` in `learning/services.py` when creating notifications
5. Create a Celery task to deliver via Slack API

### To modify the audience policy matching logic

1. Edit `audience/selectors.py` — `EligibilityService.can_view()` contains the logic
2. Add new dimension enum values to `AudienceRule.dimension` if needed
3. Test with `estimate_policy_reach()` to verify counts
4. Update console forms in `console/views.py` if needed

### To add a new gamification event type

1. Add to `ContentEvent.event_type` choices in `learning/models.py`
2. Update `learning.services.track_event()` dispatcher to handle it
3. Add point value to `GamificationSettings` in console
4. Call `track_event(user, 'NEW_EVENT_TYPE', object, ...)` from the relevant app

### To export analytics data

1. Use `AnalyticsExportAudit` model to track export history and access
2. Implement export view in console that queries `ContentEvent`, `PointLedger`, or domain models
3. Serialize to CSV/JSON and return via response (`FileResponse` or `JsonResponse`)
4. Log export to `AnalyticsExportAudit` for compliance auditing
