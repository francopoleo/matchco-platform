Arquitetura Multi-Tenant com Subdomain Routing

Data: 2026-09-29
Autor: Franco / Claude Code
Status: Recomendação de Arquitetura para Produção

1. Análise: Subdomain vs Path-Based Routing

Implementação Atual

O sistema MatchCo usa django-tenants com uma abordagem domain-based (amigável a subdomain):

TENANT_MODEL = 'configuration.Organization'
TENANT_DOMAIN_MODEL = 'configuration.Domain'
Middleware: TenantMainMiddleware (detecção automática de tenant)

Cada Organization pode ter múltiplos registros de Domain, permitindo roteamento flexível.

2. Comparação Detalhada

Opção A: Roteamento por Subdomain

Padrão: shopping.br.matchco.app, hospital.br.matchco.app, pharmacy.br.matchco.app

Vantagens

Isolamento máximo: Cada tenant tem sua própria entrada DNS — sinais claros de separação
Escopo de Cookies: Cookies específicos do domínio; sem compartilhamento acidental
Limite de Segurança: Navegadores tratam subdomínios como origens separadas — XSS em um subdomain não toca outro
Clareza de Analytics: Estrutura de URL identifica tenant imediatamente (logs, roteamento CDN)
Wildcard SSL: Um certificado wildcard (*.br.matchco.app) cobre todos os subdomínios
SEO: Cada tenant obtém sua própria autoridade de domínio (se público)
Personalização de Marca: Fácil usar domínios customizados depois (shopping.local.br em vez de subdomain)

Desvantagens

Overhead DNS/Infraestrutura: Criar entrada DNS para cada tenant (ou usar wildcard, exigindo wildcard SSL)
Complexidade de Desenvolvimento: Dev local precisa de entradas /etc/hosts ou DNS local (ex: dnsmasq)
Complexidade CORS: Se frontend e API em subdomínios diferentes, CORS deve permitir ambos
Certificados Wildcard: Necessários para cobrir todos; nem todas as CAs suportam renovação automática
Debugging: Identificação de tenant ocorre na camada HTTP; mais difícil localizar issues nos logs

Perfil de Segurança

  • Melhor: Namespaces de cookies isolados, origens de navegador separadas
  • Risco: Se cert TLS wildcard for comprometido, todos os subdomínios em risco
  • Típico em: Plataformas SaaS (Slack: workspace.slack.com, Notion: workspace.notion.so)

Opção B: Roteamento por Path

Padrão: matchco.app/shopping, matchco.app/hospital, matchco.app/pharmacy

Vantagens

Uma entrada DNS: Um registro DNS e um cert TLS para toda plataforma
Desenvolvimento: Testes locais fáceis; sem truques de /etc/hosts
Simplicidade: Parsing de URL (middleware Django) é direto
Custo: Um domínio = um cert = custos de infraestrutura menores
CORS: Uma origem simplifica requisições cross-origin
Visibilidade de Tenant: Slug do tenant visível em toda URL; mais fácil auditar e debugar
Adição de Tenant Dinâmica: Novos tenants funcionam imediatamente sem mudanças DNS/cert

Desvantagens

Compartilhamento de Cookies: Todos os paths sob matchco.app compartilham cookies — precisa isolação explícita
Origem do Navegador: Todos os tenants na mesma origem — XSS em um path pode acessar outro
Separação Visual Menos Clara: Usuários podem não perceber limites entre tenants
Complexidade de Roteamento de URL: Deve rotear cuidadosamente públicas vs autenticadas (prevenir /hospital/candidato/ de acessar /shopping/candidato/)
Analytics: Mais difícil fatiar por tenant sem lógica adicional (parsing de logs vs Host header claro)
Marca: Mais difícil usar domínios customizados por tenant (ainda mapearia para /tenant-slug)

Perfil de Segurança

  • Adequado se: Isolamento de session e middleware filtram corretamente por tenant (MatchCo já faz isso com FK Organization)
  • Risco: Vazamento acidental de dados entre tenants por filtro org faltando em uma view
  • Típico em: Plataformas internas, SaaS com controle dev mais apertado

3. Recomendação para MatchCo

Escolher Roteamento por Subdomain (Direção Atual)

Por quê:

  1. Recrutamento Público: A signup pública de candidatos (candidato.signup.br) e portal de empregador devem parecer serviços distintos → subdomínios reforçam isso
  2. Lançamentos Multi-Setor: Shopping centers, hospitais e farmácias precisam diferenciação de marca → cada setor obtém seu próprio subdomain
  3. Escalabilidade: Se MatchCo quiser domínios customizados por cliente depois (ex: careers.shoppingXYZ.com.br), subdomínios fornecem essa infraestrutura
  4. Compliance Regulatório: Auditorias LGPD beneficiam-se de separação clara em nível DNS/host
  5. Modelo Mental da Equipe: "Esta é uma instância separada rodando para um cliente específico" → mais fácil raciocinar do que path-based multi-tenancy

Padrão de Implementação (Sistema MatchCo Atual)

Infraestrutura:
├── *.br.matchco.app (DNS wildcard)
├── Cert TLS wildcard
└── Uma instância django-tenants

Modelo de Domínio (Django):
└── Organization (parent de tenant)
    ├── name: "Shopping XYZ"
    ├── slug: "shopping-xyz"
    └── domains (FK Domain model)
        ├── domain: "shopping-xyz.br.matchco.app"
        ├── is_primary: True
        └── [futuro] domain: "careers.shoppingxyz.com.br"

4. Implementação Atual do Sistema MatchCo

Detecção de Tenant

Request → TenantMainMiddleware
  ↓
Extrair Host header → Query tabela Domain
  ↓
Carregar Organization (tenant)
  ↓
Contexto de schema/banco do tenant setado

Isolamento de Schema

  • Schema compartilhado (public): Users, Domains, Organizations, permissions
  • Schemas de tenant (por organization): Todos os modelos de recruitment (CandidateProfile, Relation, Position, etc)
Regra de contexto: a organização selecionada no Console é a fronteira de todas as telas de recrutamento. Empresas, lojas/unidades, funções canônicas, QRs, necessidades, interesses e perfis relacionados são filtrados por essa organização. Um usuário vinculado a uma unidade vê apenas os registros da própria unidade; o Portal aplica a mesma regra ao carregar lojas, funções e oportunidades.

Estrutura de URL

Routes Públicas (sem /console/): - /candidato/signup → Signup de recrutamento - /oportunidades → Feed de candidatos - /matchco/ → Landing page MatchCo - /qr/<entry_point_id>/ → Entrada por QR code

Routes Privadas (autenticadas): - /portal/necessidades/ → Necessidades de alto giro e rodadas de convite

Pré-requisitos

  • Domínio alocado: shopping-example.br.matchco.app
  • Cert TLS cobre domínio (via wildcard)
  • Admin tem acesso de superuser

Procedimento Passo a Passo

Fase 1: Criar Organization (Admin)

python manage.py shell

from configuration.models import Organization, Domain

# 1. Criar Organization
org = Organization.objects.create(
    name='Shopping Example SA',
    slug='shopping-example',
    active=True,
)

# 2. Criar Domain primária
Domain.objects.create(
    domain='shopping-example.br.matchco.app',
    tenant=org,
    is_primary=True,
)

# 3. Verificar
print(f"Organization: {org.slug}")
print(f"Domain: shopping-example.br.matchco.app")

Fase 2: Importar Lojas & Funções

# Preparar CSV: stores.csv
# Name,Latitude,Longitude,Network
# Loja A,-23.564,-46.652,Network A
# Loja B,-23.560,-46.658,Network B

python manage.py shell

from recruitment.domain_models import RecruitmentStore, RecruitmentCompany, RecruitmentJobFunction
from configuration.models import Organization
import csv

org = Organization.objects.get(slug='shopping-example')
company, _ = RecruitmentCompany.objects.get_or_create(
    organization=org, name='Shopping Company',
)

# Importar lojas
with open('stores.csv') as f:
    for row in csv.DictReader(f):
        RecruitmentStore.objects.create(
            organization=org,
            company=company,
            name=row['Name'],
            latitude=float(row['Latitude']),
            longitude=float(row['Longitude']),
        )

# Importar funções
functions = ['Atendente de caixa', 'Repositor', 'Vendedor', 'Gerente de loja']
for fname in functions:
    RecruitmentJobFunction.objects.get_or_create(
        organization=org, company=company, name=fname,
    )

print(f" {RecruitmentStore.objects.filter(organization=org).count()} lojas importadas")
print(f" {RecruitmentJobFunction.objects.filter(organization=org).count()} funções importadas")

Fase 4: Seed Entry Points (QR Codes)

python manage.py shell

from recruitment.models import EntryPoint
from recruitment.domain_models import RecruitmentStore
from configuration.models import Organization
from django.utils import timezone

org = Organization.objects.get(slug='shopping-example')
stores = RecruitmentStore.objects.filter(organization=org)

for store in stores:
    # Entry Point Match (matching bilateral)
    EntryPoint.objects.get_or_create(
        organization=org,
        label=f'QR Match · {store.name}',
        defaults={
            'kind': EntryPoint.KIND_STORE,
            'scope_store': store,
            'mode': EntryPoint.MODE_MATCH,
            'canonical_destination_url': f'https://shopping-example.br.matchco.app/qr/...',
            'activation_tested_at': timezone.now(),
            'state': EntryPoint.STATE_ACTIVE,
        },
    )

    # Entry Point Match (necessidades de alto giro)
    EntryPoint.objects.get_or_create(
        organization=org,
        label=f'QR Match · {store.name}',
        defaults={
            'kind': EntryPoint.KIND_STORE,
            'scope_store': store,
            'mode': EntryPoint.MODE_MATCH,
            'canonical_destination_url': f'https://shopping-example.br.matchco.app/qr/...',
            'activation_tested_at': timezone.now(),
            'state': EntryPoint.STATE_ACTIVE,
        },
    )

print(f" Entry points criados para {stores.count()} lojas")

10. Checklist de Segurança

Isolamento Multi-Tenant

  • TenantMainMiddleware ativa contexto de schema do tenant
  • Todas as queries filtram por organization=request.organization
  • Auditoria: Amostragem aleatória de queries de console para verificar filtro org
  • Nenhuma raw SQL query sem comentário TENANT SAFE

Prevenção de Vazamento de Dados

  • Endpoints de API requerem validação de parâmetro organization
  • Middleware de session não compartilha dados de session entre orgs
  • Uploads de arquivo armazenados em caminhos específicos de org
  • Exportação de dados LGPD respeita limites de organização

Certificado & DNS

  • Cert wildcard (*.br.matchco.app) emitido
  • Registros CAA de DNS configurados (autorizar letsencrypt)
  • Renovação de cert automatizada (Certbot hooks)
  • TLS 1.2+ obrigatório

Estrutura SaaS unificada: shopping, rede, lojas e recrutamento

O recrutamento Match é um módulo da mesma estrutura SaaS. A fonte canônica é Organization → empresa/parceiro → unidade → área/departamento → função → Membership/audiência. As tabelas paralelas de organização, empresa e loja de recrutamento não devem receber novos cadastros.

Console: Organização e Estrutura são uma única categoria de navegação. A visão geral, dados da organização, marca, integrações, empresas, unidades, áreas, funções, canais e tipos de pessoa pertencem ao mesmo núcleo e sempre usam a organização selecionada no topo.

Diferença de escopo: a visão geral da organização é o único hub do tenant e fica em /console/organization/; /console/ permanece apenas como entrada compatível e redireciona para ele. A Administração global (/console/admin/) é exclusiva da plataforma e agrega organizações, usuários, conteúdo e métricas; ela não substitui nem duplica a administração da organização.

Distinção de cadastro: Cargos e funções respondem “o que esta pessoa faz” — por exemplo, vendedor, farmacêutico ou técnico de suporte. Tipos de público e vínculo respondem “qual é a relação dela com a organização” — por exemplo, colaborador, lojista, prestador ou parceiro. O segundo não é um cargo e não deve ser usado para o de-para canônico do recrutamento; ele participa da audiência, do Membership e das permissões do Talk.

Exemplo: a Drogasil do Bourbon aponta para um único local físico, mas possui uma representação na organização Bourbon e outra na organização Rede Drogasil. Conteúdo, Talk, cursos, usuários e audiências continuam isolados; o compartilhamento depende de Membership e aprovação próprios.

1. Bourbon

Áreas internas, lojistas e prestadores do shopping.

2. Drogasil

Rede, unidades, áreas e programas próprios.

3. Local físico

Um local real, duas representações contextuais.

4. Recrutamento

Necessidades usam a mesma unidade e função canônica.

Os cenários oficiais de desenvolvimento são Bourbon Shopping, Rede Drogasil e ElectraTech Eletrônicos. O reset recria diretamente a base canônica; não há dados de produção a preservar.

Catálogo local: funções canônicas são globais para permitir padronização, mas o vínculo cargo/unidade é específico. A Centauro não recebe “Farmacêutico(a)” só porque a função existe na organização Bourbon; a Drogasil do mesmo shopping possui seus próprios vínculos na representação Drogasil. Recrutamento é um serviço opcional: em organizações que usam apenas Talk, cursos ou comunicação, a estrutura não mostra colunas, atalhos ou telas de Match.

Ponte com o candidato: há uma única origem para cada tipo de informação. /console/job-functions/ cadastra o cargo oficial da empresa e seus canais estruturais. O catálogo Match da unidade, aberto por Configurar Match em Unidades de negócio ou pela entrada operacional /portal/gestao/funcoes/, associa esse cargo a uma ou mais funções canônicas do formulário do candidato e mantém descrição, requisitos, benefícios e condições de contratação. A necessidade consulta somente esse vínculo; o motor compara os termos canônicos com as funções declaradas no Perfil. Assim, o cargo não é duplicado e o de-para continua específico da unidade.

Local físico e contexto: um local real é representado por PhysicalLocation no núcleo e pode ter mais de uma representação contextual. A Drogasil do Bourbon, por exemplo, aponta para o mesmo local físico nas organizações Bourbon Shopping e Drogasil Rede; empresas, usuários, conteúdos, audiências e permissões continuam separados por organização.

Cadastro canônico de unidade ou loja

A unidade é o registro operacional que organiza pessoas, serviços, conteúdos e, quando ativado, necessidades de Recrutamento. O cadastro atende loja de rua, loja em empreendimento, quiosque, serviço, escritório, centro de distribuição, fábrica e unidade parceira.

Identificação

Empresa, nome operacional, nome comercial, código, referência externa, tipo de unidade e canal.

Localização

Rua ou shopping, local físico compartilhável, endereço, número, complemento, bairro, cidade, UF, CEP e coordenadas.

Operação

Responsável, telefone, e-mail, site e horário de funcionamento.

Administrativo

CNPJ e inscrição estadual, quando necessários. Esses dados não aparecem para candidatos.

Regra de endereço: uma loja dentro do Bourbon pode usar o endereço do empreendimento e apontar para o mesmo PhysicalLocation. Uma Drogasil de rua mantém seu próprio endereço e CEP. Em um centro de distribuição ou fábrica, o tipo de unidade e a localização industrial deixam o contexto explícito. O CEP da unidade e o CEP do candidato ficam disponíveis apenas para cálculo controlado de proximidade e administração autorizada.

Regra de serviço: Talk, Conteúdo e Treinamento podem usar o cadastro da unidade sem Recrutamento ativo. O de-para para funções canônicas só aparece como extensão do Match quando o serviço estiver ativo para a organização.

Validação de segurança: a tela filtra empresa, unidade e função, mas o domínio também valida o pertencimento. Uma necessidade não pode combinar unidade ou função de outra organização, e uma Relation não pode combinar Perfil e oportunidade de tenants diferentes. Isso protege o SaaS mesmo quando uma integração ou chamada interna não passa pela tela.

Serviços modulares do SaaS

Ativação modular: a organização e sua estrutura são o núcleo do produto. Conteúdo, Talk, Treinamento, Certificação, Recrutamento Match, Campanhas, Operação e Indicadores são serviços ativáveis sobre o mesmo tenant, com Membership, audiência, escopo, auditoria e LGPD compartilhados. Em /console/organization/services/, o administrador define o padrão da organização e pode criar uma exceção por empresa. A empresa herda o padrão enquanto não tiver uma configuração própria; uma suspensão ou ativação explícita da empresa vale somente para ela. Quando Recrutamento não está ativo no escopo aplicável, o Console não mostra o grupo Match nem seus atalhos.

Autonomia de conteúdo por empresa: o Console é a administração editorial; o Portal atende operações autorizadas; e o App autenticado é a experiência de consumo de Feed, Wiki, cursos e documentos. Cada conteúdo pode pertencer à organização ou a uma empresa. Conteúdo organizacional pode ser compartilhado dentro do tenant conforme a audiência; conteúdo empresarial exige Membership da empresa correspondente ou administração organizacional e continua sujeito à audiência. A fronteira é aplicada no servidor também em detalhes, arquivos, ações em lote, eventos e sincronização móvel — não depende do filtro visual. Ser staff ou pertencer a um grupo editorial, por si só, não libera dados de outra empresa. Um link de compartilhamento é uma concessão explícita à parte, com validade e escopo controlados.

Exemplo Drogasil no Bourbon: o shopping pode entregar conteúdo operacional à unidade pelo Membership Bourbon; a Rede Drogasil pode entregar Talk e Treinamento pelo Membership Drogasil. Ativar um serviço não copia usuários ou conteúdo e não herda a audiência da outra organização.

Comercialmente, Conteúdo e Talk podem formar um pacote de Comunicação, enquanto Treinamento e Certificação formam Aprendizagem. Tecnicamente, as capacidades continuam separadas para permitir que cada organização contrate somente o que precisa.

Plano de implementação incremental

A estrutura atual permanece a base do produto. A implementação será feita por adaptação e isolamento, sem criar uma segunda hierarquia para organizações, empresas, unidades, usuários ou funções.

0 — Base limpa

Contrato canônico e três cenários recriados diretamente.

1 — Núcleo

Organização, empresa, unidade, área, função e Membership.

2 — Contexto

Local físico compartilhado e representações isoladas.

3 — Acessos

Convites, audiências, validade, revogação e auditoria.

4 — Serviços

Conteúdo, Talk, Aprendizagem e Match sobre o núcleo.

5 — Expansão

Parceiros, Operação, Campanhas e Indicadores depois do núcleo.

11. Plano de Rollback

Se um tenant precisa ser desativado:

# Soft delete (preserva dados)
org = Organization.objects.get(slug='shopping-xyz')
org.active = False
org.save()

# Dados permanecem no schema do tenant; subdomain para de resolver
# Para restaurar: org.active = True

Se remoção completa for necessária:

# Backup primeiro!
python manage.py dumpdata recruitment.* --indent 2 > shopping-xyz-backup.json

# Depois dropar schema (se usando PostgreSQL)
psql -c "DROP SCHEMA shopping_xyz CASCADE;"

Idiomas e localização

O idioma da interface é uma preferência de apresentação, independente da organização ativa, do serviço contratado e das permissões. Português do Brasil é o padrão, mesmo que o navegador esteja em outro idioma; a pessoa pode selecionar Inglês ou Espanhol nas páginas públicas, no menu da conta ou em Configurações, e a preferência é aplicada nas próximas páginas. A cobertura de Inglês ainda está pendente e a de Espanhol é parcial. Conteúdos publicados por uma empresa — como cursos, Feed, Wiki, documentos e descrições — permanecem no idioma em que foram escritos, salvo se houver uma tradução editorial explícita.

Ao incluir uma linguagem, é necessário traduzir e revisar as jornadas públicas e autenticadas, compilar os catálogos e testar o fallback. Não se deve inferir que o idioma está completo apenas porque aparece no seletor.

Roteamento por subdomain é a escolha correta para expansão multi-setor do MatchCo
Implementação atual do MatchCo já suporta isso (django-tenants + modelo Domain)

Plano de escalabilidade: estrutura SaaS canônica, unidade física compartilhada com memberships isolados e branding por tenant
Segurança: Todas as reviews aprovadas; filtragem org-level adequada em todo lugar
